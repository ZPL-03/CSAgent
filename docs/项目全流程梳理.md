# 项目全流程梳理

## 项目定位

CSDM_cph 是复合材料外压圆柱耐压壳智能设计系统。系统以多智能体编排为主线，把自然语言需求转为结构化设计任务，生成候选方案，完成代理模型初筛，执行真实 ABAQUS 有限元校核，写入案例库并导出设计报告。

运行事实源位于本项目目录内。模型接口、知识库、案例数据、公式系数、材料库和任务契约均读取本项目文件。

## 运行环境

- Conda 环境：`GPT`
- Windows 解释器：`D:\anaconda3\envs\GPT\python.exe`
- GUI 入口：`main.py`
- 环境自检：`scripts/check_env.py`
- 主模型配置：项目根目录 `.env` 中的 `LLM_PRIMARY_URL`、`LLM_PRIMARY_API_KEY`、`LLM_PRIMARY_MODEL_NAME`
- 回退模型配置：项目根目录 `.env` 中的 `URL`、`API_KEY`、`MODEL_NAME`
- 工作站领域模型接口示例：`LLM_PRIMARY_URL=https://csllm.ipen03.com/v1`，`LLM_PRIMARY_MODEL_NAME=csllm`

所有脚本、GUI、测试和环境检查均使用 `GPT` 环境。

## LLM 职责边界

主模型是领域微调模型 `csllm`。该接口用于领域候选提案和报告工程解释，不作为流程控制或工程数值事实源。候选生成 LLM 会读取外部知识库/知识图谱检索片段，用于补充工程提案依据；候选结构化参数仍由系统解析、归一化、规则检查和 Schema 校验确定。

| 模块 | LLM 职责 |
| --- | --- |
| `TaskParser` | 不调用 LLM；候选池数量、Top-K、载荷、几何、目标压力由规则解析得到 |
| `CandidateGenAgent` | 生成 LLM 来源候选提案；输入为系统整理后的工程任务书，包含用户已给事实、外部知识库/知识图谱片段、LLM 候选数量、输出字段要求和系统候选字段约束；输出为自然语言候选表，由系统解析为结构化候选 |
| `ReportGenAgent` | 任务事实、候选编号、数值和有限元结论由结构化数据确定性生成；工程解释与制造建议可调用 LLM 做定性解释，约束清理后仍异常时退回确定性解释 |
| `ScreenerAgent` | 不调用 LLM |
| `FEMAgent` | 不调用 LLM |
| `KnowledgeAgent` | 不调用 LLM |
| `ConversationFlowController` | 不调用 LLM，进度说明由确定性模板生成 |

## GUI 输入与任务控制

GUI 左侧只输入自然语言设计需求。需求中必须明确给出候选池总数和初筛保留数量，例如“生成 12 个候选，初筛保留 5 个候选”。任一数量缺失时，系统不启动主流程。

候选池数量和初筛保留数量是任务参数，不是固定值。系统按当前任务的 `total_candidates` 和 `top_k_candidates` 执行。

候选来源使用默认初始比例 `LLM:案例迁移:DOE = 2:1:1`。该比例只用于计算三条来源的初始目标配额，例如候选池总数为 12 时，初始配额为 LLM 6 个、案例迁移 3 个、DOE 3 个。实际候选来源统计以规则检查后的有效输出为准；当领域主模型合规输出不足或正式案例库中可迁移案例少于初始配额时，实际来源拆分会变化，候选池总数由 DOE 参数采样完成数量闭合。

任务解析会额外生成 `user_input_facts`。该字段只记录用户自然语言明确给出的事实，包括候选池总数、初筛保留数、外压、边界、材料和目标压力。用户在普通需求中写出的长度、半径、厚度、铺层角或缺陷比进入 `geometry_reference`，作为设计中心和几何包络依据，不强制所有候选等于该数值；只有自然语言明确写出固定、限定、保持不变、必须等于等约束时，相关字段进入 `fixed_geometry`。系统内部为规则检查、DOE、候选变量完整性和有限元准备的工程域参数不写入 `user_input_facts`，也不作为用户事实发送给候选生成 LLM。

## 全流程

### 1. 启动与目录准备

`main.py` 调用 `ensure_project_dirs()` 确保 `data/`、`knowledge/`、`models/`、`docs/` 和 ABAQUS 运行目录存在，然后启动 PyQt6 主界面。

### 2. 任务解析

`ConversationFlowController.start()` 接收 GUI 输入，调用 `OrchestratorAgent.parse_instruction()`。`TaskParser` 执行规则解析，不调用领域主模型。规则解析得到以下字段：

- 外部静水压力
- 边界条件
- 长度、半径、厚度、铺层角、缺陷比参考值或固定约束
- 极限压力目标
- 候选池总数
- 初筛保留数

GUI 与编排器主流程会将解析结果写入 `data/tasks/TASK_N.json`，编号按现有任务文件顺延。`task_id` 是会话追溯字段，不是案例主身份字段；历史导入、批量建库和底层脚本生成案例时，如果没有真实任务来源，案例记录不写入 `task_id`。

`TaskParser` 使用规则解析生成任务契约。内部工程默认值只用于任务契约完整性、DOE 参数域、规则检查、候选变量完整性和有限元接口，不进入 `user_input_facts`。普通几何数值形成 `geometry_reference` 和 `geometry_envelope`，用于引导候选靠近用户关心的尺度；明确固定的几何数值形成 `fixed_geometry`，用于候选约束和固定范围。候选生成 LLM 读取 `user_input_facts`、外部知识库/知识图谱片段和 LLM 目标候选数；提示词要求模型把非固定几何写成候选建议值，而不是用户已给固定条件。

### 3. 候选方案生成

`CandidateGenAgent` 组织三类来源：

| 来源 | 作用 |
| --- | --- |
| `LLM` | 基于用户已给事实生成自然语言候选方案表 |
| `CASE_TRANSFER` | 从正式案例库检索相近通过案例并绑定当前任务约束 |
| `DOE` | 在参数范围内进行确定性采样，提供参数空间覆盖 |

三路来源均属于候选池组成部分。初始目标配额按 `config/app_config.yaml` 中的 `pipeline.candidate_source_ratio` 计算。实际进入候选池的数量以有效候选为准：

- LLM 输入不是原始用户自然语言，而是系统整理后的工程任务书：任务书写明需要生成多少套 LLM 来源候选，列出 `user_input_facts` 中的用户已给信息、输出字段要求和系统候选字段约束。
- 系统候选字段约束只描述项目材料库、参数域、单位和可解析铺层格式，用于防止模型输出无法校核的候选；这些约束不进入 `user_input_facts`，也不能被模型叙述为用户已给事实。
- 外部知识库/知识图谱片段只作为 LLM 工程提案依据，不作为用户已给事实，不直接写入结构化候选。
- LLM 输出保持训练数据中的自然语言工程回答风格，通常包含候选方案表、筛选逻辑和制造/FEM 建议。候选表中的推荐理由需要同时说明结构性能依据和制造/缺陷风险依据。系统从自然语言表格或编号方案中提取材料、长度、半径、厚度、alpha、beta、缺陷比和铺层表达式；候选编号列不参与材料解析。
- LLM 输出的候选行保存到 `origin_summary`，回答原文保存到 `llm_output_excerpt`，用于 GUI 查看和候选来源追踪。
- LLM 候选的材料、长度、半径、厚度、alpha、beta、缺陷比必须在结构化候选中完整存在。`geometry_reference` 不会覆盖 LLM 候选参数；`fixed_geometry` 会覆盖对应候选参数并形成固定几何约束。
- LLM 候选缺少材料、长度、半径、厚度、alpha、beta 或缺陷比时不进入候选池，系统不使用通用默认几何或材料库补齐这些主设计字段。
- LLM、案例迁移和 DOE 三路候选按材料、几何变量和铺层表达式形成结构等价签名；签名重复的候选不进入候选池，候选池缺口由 DOE 继续补足。
- 案例迁移只使用正式案例库中通过有限元校核、工况边界匹配、材料兼容的真实案例。
- 案例迁移不把同一条案例复制成多个迁移候选；可迁移案例少于初始配额时，实际案例迁移数量随之减少；案例设计缺少必要几何字段时直接跳过，不使用默认几何补齐。
- DOE 按参数域采样承担参数空间覆盖，并在 LLM 或案例迁移有效数量不足时完成候选池数量闭合。

每个候选都会执行：

- 几何范围归一化
- 铺层格式归一化
- 铺层模板修复
- 材料体系绑定
- 规则检查
- JSON Schema 校验

候选会话编号使用 `TMP_N`，候选阶段的 `candidate_id` 与 `display_name` 都写为该会话编号，不写空的 `persistent_candidate_id`。进入有限元前，正式候选编号使用 `C_N`，按已有案例编号顺延；正式输入的 `candidate_id` 与 `display_name` 都写为正式编号，并通过 `session_candidate_id=TMP_N` 回溯会话候选。有限元结果落盘后同步保留 `session_candidate_id`，后续报告和案例追溯不依赖 GUI 内存态。

### 4. 代理模型初筛

`ScreenerAgent` 对候选池逐个计算代理结果。该阶段不调用 LLM。

ASME RD-1172 线性屈曲压力由 `core/pressure_hull_profile.py` 计算，字段为 `asme_linear_buckling_pressure_MPa`，在 PBIPF 公式中记为 `Q`。

极限压力使用 PBIPF 公式：

```text
P_PBIPF = d1 * lg(Q) * t / R
        + d2 * Q * D22 / (D33 - D12)
        + d3 * Q * Ir * L / A22
        + d0
```

排序分数为：

```text
score = pressure_weight * P_ult
      - weight_penalty * 面密度
      - uncertainty_penalty * 公式不确定度
```

初筛保留数量使用当前任务的 `top_k_candidates`，并受候选池实际数量上限约束。

### 5. 有限元校核

`FEMAgent` 将入选候选转为 ABAQUS 输入，执行真实有限元校核。该阶段不调用 LLM。

有限元包含两个阶段：

1. 单位外压线性屈曲分析，输出一阶线性屈曲压力和一阶模态云图数据。
2. 以一阶模态作为几何缺陷进入 Static Riks 后屈曲分析，极限压力取最大 LPF 与基准外压的乘积。

结果字段包括：

- `linear_buckling_pressure_MPa`
- `ultimate_pressure_MPa`
- `riks_lpf_max`
- `imperfection_amplitude_mm`
- `visualization_json`
- `linear_buckling_odb`
- `postbuckling_odb`
- `verdict`

未找到 ABAQUS 命令或求解失败时返回诊断结果，不生成虚假通过结果。

### 6. 案例与知识回流

`KnowledgeAgent` 写入案例记录。该阶段不调用 LLM。

案例编号使用 `CASE_N`，与正式候选编号 `C_N` 对应。通过校核的案例进入 `knowledge/case_library` 和案例记忆索引；未通过或求解失败的案例只进入评估档案。案例记录有真实会话来源时保留 `task_id`，没有真实会话来源时不写该字段。

案例设计保存正式 `candidate_id`、正式 `display_name` 和可用的 `session_candidate_id`，不保存重复的 `persistent_candidate_id`。案例记录包含：

- 结构化任务
- 设计参数
- 代理模型初筛字段
- 有限元结果
- 代理预测误差
- 结论与诊断说明

### 7. 报告输出

`ReportGenAgent` 汇总任务、初筛理由、有限元结果和工程建议，输出：

- `data/results/latest_report.md`
- `data/results/latest_report.pdf`

任务事实、外压、目标压力、候选编号、代理模型初筛字段和有限元结论由结构化数据直接写入。工程解释与制造建议段可调用 LLM，输入只包含结构化任务、入选候选和有限元结果，提示词要求定性解释铺层、制造工艺、缺陷控制和验证建议。LLM 输出出现结构化输入之外的新数值、阈值或材料牌号时先做约束清理；清理后仍不合规或调用失败时，报告使用确定性工程解释。

报告导出面向已有有限元校核结果，可作为阶段报告使用；未校核候选仍保留在当前候选集中，不进入有限元结果章节和结论统计。

## 知识库与知识图谱

运行时读取本项目知识资产：

- 知识库文本块：`knowledge/external/rag/rag_chunks.jsonl`，51788 条
- 知识图谱实体与关系：`knowledge/external/kg`，2214 个实体、480899 条关系
- 源登记与源元数据：`knowledge/external/provenance/source_registry/`，各 1931 条
- 结构化文档：`knowledge/external/provenance/structured_text/documents.jsonl`，1931 条
- 结构化文本块：`knowledge/external/provenance/structured_text/blocks.jsonl`，400762 条
- 表格、图片和公式记录：`table_records.jsonl` 22800 条，`figure_records.jsonl` 44135 条，`formula_records.jsonl` 108500 条
- Markdown 全文：`knowledge/external/provenance/structured_text/markdown_documents/`，1931 份

候选生成 LLM 接收用户已给事实、LLM 候选数量、输出字段要求和外部知识库/知识图谱检索片段。检索片段用于说明结构性能、制造风险和缺陷敏感性依据，不接收系统默认参数作为用户事实，也不直接作为结构化候选参数来源。RAG 片段按同一篇文献或同一来源去重，图谱证据合并为统一来源标签；`provenance/` 用于人工核查源登记、结构化记录和完整 Markdown 上下文。初筛、有限元和案例记录不依赖 LLM 对知识片段的解释。

## 编号规则

| 对象 | 编号 | 位置 |
| --- | --- | --- |
| 任务追溯 | `TASK_N` | `data/tasks`，仅 GUI 与编排器主流程产生真实会话任务时写入 |
| 会话候选 | `TMP_N` | 内存与 GUI 表格 |
| 正式候选 | `C_N` | 有限元输入与结果 |
| 案例 | `CASE_N` | `data/cases`、`knowledge/case_library` |

正式候选和案例编号均按已有文件最大编号顺延。会话候选仅使用 `TMP_N`，不占用正式候选和案例编号。会话候选显示名等于 `TMP_N`，正式有限元输入和案例设计显示名等于 `C_N`。案例编号、案例迁移检索和案例记忆索引不依赖 `task_id`；案例契约保留 `task_id` 属性，但不要求每条案例都包含该字段。
